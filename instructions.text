Project Document: Git Account Manager (AccMngr)1. Project Aim and Motivation1.1. 🎯 Primary GoalTo build a super-lightweight, high-performance, and secure command-line utility in Rust that automates the complex configuration required to manage multiple Git profiles (Work, Personal) on a single machine.1.2. ✨ Value PropositionAccMngr eliminates manual errors and security risks by:Automating Authentication: Securely manages and assigns the correct SSH key for each profile using configuration aliases.Guaranteeing Identity: Ensures the correct, verified email is used for every commit, solving attribution issues.Cross-Platform Portability: Using Rust and the Hexagonal Architecture allows for easy future migration to desktop (Tauri/Wails) and support for multiple Git providers.2. 🏗️ Architectural Design: Hexagonal Architecture (Ports & Adapters)The application will strictly adhere to the Hexagonal Architecture pattern to decouple the core business logic from external dependencies (APIs, OS, UI). This ensures extensibility (switching providers) and testability.2.1. The Core (The Hexagon)This layer contains the unpolluted business logic and domain entities. It does not depend on any external crate like reqwest or std::fs.ModuleResponsibilityKey Rust Constructsdomain::entityDefines core data structures.struct Profile { id, name, email, auth_host: String }, struct SshKey { public_key: String }domain::portsDefines the contracts (interfaces) for interaction.Traits like trait AuthProviderPort (for API access) and trait SystemIOPort (for file access).domain::use_casesImplements the application logic (what the app does).Functions like add_profile(), switch_profile(), sync_config().2.2. The Adapters (External Infrastructure)These modules implement the traits defined in the domain::ports.AdapterTypeResponsibilityExtensibility Focusadapters::githubDriven (Secondary)Implements the AuthProviderPort trait using GitHub's REST API (reqwest/tokio). Handles OAuth and key uploads.Future: Easily replaceable by adapters::gitlab or adapters::bitbucket.adapters::system_ioDriven (Secondary)Implements the SystemIOPort trait. Executes ssh-keygen, reads/writes ~/.ssh/config, and manages local profile storage.Future: Swap for a mock adapter during unit testing or a specialized Windows adapter.adapters::tuiDriving (Primary)Implements the Ratatui UI. Receives user input and calls the appropriate function in the domain::use_cases.Future: Easily replaced by adapters::tauri for a desktop GUI.3. ⚙️ Rust Best Practices and Tooling3.1. Error Handling (thiserror and anyhow)Principle: Use structured error handling to provide clear, actionable feedback to the user.Practice: Define a custom enum AppError (using thiserror) in the domain module. Use anyhow for simple error propagation in the main function and adapter code.3.2. Asynchronous Execution (tokio and reqwest)Principle: All I/O-bound tasks (API calls, running the local OAuth server) must be non-blocking to maintain TUI responsiveness and speed.Practice: Use the tokio runtime for the application entry point. All adapter functions dealing with the network or file system should be async and utilize the reqwest HTTP client.3.3. Key Crates to LeverageCratePurposeclapRobust CLI argument parsing and help generation.ratatuiRendering the Text User Interface (TUI) for the MVP.tokioAsynchronous runtime for high-performance I/O and concurrency.reqwestSecure, asynchronous HTTP client for GitHub API calls.serdeSerialization and deserialization of JSON data (for API responses and local config files).regexSafely parsing and editing text-based configuration files (~/.ssh/config).3.4. Secure Sensitive DataPrinciple: Do not store plain text private keys or access tokens in common memory longer than necessary.Practice: The Access Token should be stored securely on the local machine (e.g., using OS-specific secrets management if possible, or a local encrypted file, managed by the system_io adapter). SSH keys must be handled as secure file paths and never logged.
